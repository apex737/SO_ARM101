## 무엇을 왜 하는가
실제 로봇·정책이 준비되기 전에, 주문을 받고·검증하고·대기열에 넣고·실행하고·실패를 처리하고·결과를 남기는 "신뢰성 뼈대"를 만든다.
로봇 동작은 드라이버 인터페이스 뒤에 숨기고 Mock 드라이버로 성공/실패/무응답을 재현해 이 PC에서 검증한다.
S03 이후 실제 드라이버를 같은 인터페이스로 끼운다.

## 사전 통과 기준
Mock 드라이버, 임시 SQLite DB, pytest(FastAPI TestClient)로 확인한다. 각 항목은 자동 시험 하나 이상으로 대응한다.
1. 정상 접수: 유효한 주문 → 202, order_id·status=QUEUED 응답. 요청 원문·응답이 api_requests에 저장된다.
2. 요청 거절: 모르는 색, qty 0/한도 초과, 빈 items, 정의되지 않은 필드, 깨진 JSON → 422. 주문은 생성되지 않고 거절 요청도 감사 기록에 남는다.
3. 멱등성: 같은 request_id + 같은 본문 재전송 → 200, 같은 order_id, 주문 1개만 존재. 같은 request_id + 다른 본문 → 409.
4. 대기열 한도: 대기 주문 수가 한도 이상 → 503 + Retry-After.
5. 전부 성공: red×2, blue×1 → 주문 DONE, 작업 3개 SUCCEEDED, 각 시도 1회.
6. 실패 후 재시도: 첫 시도 GRASP_FAIL → recover 호출 → 두 번째 시도 SUCCESS. 작업 SUCCEEDED, 시도 기록 2개.
7. 최종 실패: 매번 실패 → MAX_ATTEMPTS 후 작업 FAILED, 주문 FAILED, 남은 작업 SKIPPED. 다음 주문은 이어서 실행된다.
8. 복구 실패 → 로봇 FAULT, 새 작업을 집지 않음, /health에 fault 표시. POST /robot/reset 후 복구 동작 성공 시 중단된 주문을 이어서 완료.
9. 드라이버 무응답(pick이 시간 한도+여유를 넘김) → DRIVER_HUNG 기록 후 FAULT.
10. 재시작 복구: DB에 진행 중(RUNNING) 주문·끝나지 않은 시도가 남은 상태로 시작 → 시도 INTERRUPTED, recover 먼저 수행, 주문 이어서 DONE.
11. 취소: 대기 중 주문 취소 → CANCELLED, 실행 안 됨. 실행 중 취소 → 현재 작업 후 멈추고 남은 작업 SKIPPED, CANCELLED. 끝난 주문 취소 → 409.
12. 실제 서버 기동: uvicorn으로 띄운 서버에 PC 클라이언트 스크립트로 주문 → 완료까지 조회 (수동 실행 1회).

## 구현과 주요 결정
- D01 대기열 = SQLite 테이블 + 단일 작업자 스레드
  - 대안: Redis/Celery(Pi에 별도 서비스 필요, 로봇이 1대라 병렬 이점 없음), asyncio 메모리 큐(재시작 시 유실).
  - 근거: 불변 조건 "재시작해도 주문을 잃지 않음", "로봇은 한 번에 하나". 대가: 처리량 확장성 낮음. 다시 판단: 로봇이 여러 대가 될 때.
- D02 멱등성 키 = 클라이언트가 보내는 request_id (본문 해시와 함께 저장)
  - 대안: 서버가 매번 새 주문 생성(네트워크 재전송 시 중복 키트 생성).
  - 근거: PC→Pi는 무선일 수 있어 응답 유실·재전송을 가정. 대가: 클라이언트가 고유 ID를 만들어야 함.
- D03 실패 정책: 한 시도 = 집기 → 잡힘 확인 → 키트 박스에 놓기. 실패하면 recover(그리퍼 열기·대기 자세) 후 재시도, 실패 시도가 MAX_ATTEMPTS에 도달하면 작업 FAILED → 주문 FAILED, 남은 작업 SKIPPED.
  - 대안: 실패 품목만 빼고 계속(PARTIAL 키트).
  - 근거(가정): 불완전한 키트는 쓸 수 없다고 가정. 다시 판단: 부분 키트가 필요하다고 하면.
  - INTERRUPTED(재시작으로 끊긴 시도)는 실패 횟수에 넣지 않는다. 집기 실패가 아니기 때문.
- D04 물리 상태를 모르면 FAULT로 정지
  - FAULT 조건: recover 실패, 드라이버 무응답(DRIVER_HUNG), 시작 시 recover 실패. FAULT는 DB에 저장되어 재시작해도 유지된다.
  - 진행 중 주문은 RUNNING으로 남기고 작업은 PENDING으로 되돌린다. 리셋 후 recover가 성공하면 이 주문부터 이어 간다.
  - 서버 시작 시와 리셋 시 항상 recover를 먼저 실행한다(알려진 자세에서 시작).
  - 대가: 실제 로봇에서는 부팅 직후 암이 움직인다. 안전 확인 방법은 S03에서 정한다.
- D05 감사 기록: POST /orders 요청마다 원문·HTTP 상태·응답 원문·order_id를 api_requests에 저장. GET /requests가 주문의 최종 결과와 묶어 보여준다(요청 → 응답 → 실제 결과 추적).
- D06 로봇 드라이버 인터페이스 분리: connect / pick(color, deadline) / verify_grasp(color) / place() / recover() / status(). S01은 MockDriver(시나리오 주입 가능)로 검증.
- D07 비동기 응답(202 Accepted + 상태 조회)
  - 대안: 작업 완료까지 HTTP 응답 대기(수십 초 연결 유지, 타임아웃 후 재전송 시 중복 실행 위험).
- D08 드라이버 호출 시간 한도: pick에는 deadline을 넘겨 드라이버가 스스로 TIMEOUT을 반환하게 하고, 작업자는 한도+여유(grace)까지만 기다린다. 넘기면 DRIVER_HUNG → FAULT.
  - 한계: Python 스레드는 강제 종료가 안 되므로 멈춘 호출 스레드는 버리고 새 실행기를 만든다.
