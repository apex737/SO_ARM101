## 무엇을 왜 하는가
사용자 분해안 1번: 위에서 보는 웹캠으로 블록을 찾고, 계산(역기구학)으로 그리퍼를 블록 위 30~50mm로 보내고, 손목 회전을 블록 각도에 맞춘다.
2026-11-10 변경: 깊이 카메라를 쓸 수 없게 되어 웹캠 2대(위 1, 손목 1)로 진행한다. 블록은 눈에 잘 띄는 한 가지 색으로 찾는다(결정 D06). 색을 늘리는 일은 S03이 맡는다.
이 Step의 핵심 질문은 "계산으로 보낸 그리퍼가 실제로 몇 mm, 몇 도 어긋나는가, 그리고 그 상태를 ACT에 넘길 수 있는가"이다(2026-11-11 변경, D09). 접근이 정확해져도 역할 분담(접근 = CV+IK, 그 뒤 = ACT)은 바꾸지 않는다. 이전 문장: "이 숫자가 허용 오차 안이면 하이브리드로 간다. 훨씬 크고 보정으로 줄지 않으면 방향을 다시 정한다."

## 사전 통과 기준
수치 기준은 측정 전에 정한 추정값이다. 결과를 본 뒤 기준을 바꾸면 이유를 남긴다.

**꼭 실물로 확인할 것 (판정 기준)**
1. 접근 정확도: 작업 영역 격자 9곳 × 블록 각도 2종 이상(예: 0°, 30°)에서 그리퍼를 블록 위 30~50mm로 보낸다.
   - 측정: 그리퍼 중심과 블록 중심의 수평 오차(mm), 그리퍼 각도와 블록 각도 차이(°).
   - 허용 오차 = (집기 직전 벌림 폭 P16 − 블록 한 변) ÷ 2. 시작값 (45 − 25) ÷ 2 = 10mm. 최대 벌림 폭이 아니라 정해서 쓰는 벌림 폭 기준이다(2026-11-10 정정: 최대로 벌리면 옆 블록 충돌·블록 밀림).
   - 통과: 시도의 90% 이상이 허용 오차 안, 각도 오차 10° 이하 (추정 기준. 남는 오차는 ACT가 보정한다는 가정).
   - 통과하지 못하면: 원인(렌즈 왜곡·평면 보정 오차 / 시차(블록 높이) / 카메라-로봇 보정 오차 / 서보 유격)을 나눠 기록하고 "탐색 완료"로 닫은 뒤 방향을 다시 정한다.
2. 안전: 테이블 높이 아래로 내려가는 명령과 관절 한계를 넘는 명령을 실행 전에 거부한다.
3. ACT 인계 조건 (2026-11-11 추가, D09. 실물 결과를 보기 전에 정함): 별도 위치 9곳 × 각도 2종 평가에서 ① 손목 카메라에 목표가 모든 시행에서 보이고 ② 접근 높이 차이(최대 − 최소)가 10mm 이하(추정 기준). ③ 남은 오차의 최대값은 기록만 한다(시연 때 접근 목표를 흔들 범위).
- 판정 (2026-11-11 변경): 1 + 3 충족 → 통과. 1은 못 넘고 3 충족 → 남은 오차를 원인별로 기록하고 "탐색 완료"로 닫은 뒤 ACT 시연으로 넘어간다. 3을 못 넘으면 접근 단계에서 먼저 해결한다.
- 측정 방법 (2026-11-11 변경, D10): 접근 오차는 손목 카메라 사진으로 잰다. 실행 순서와 명령: [S02_FinalPlan_2026-11-11.md](S02_FinalPlan_2026-11-11.md).

## 구현과 주요 결정
- D07 카메라 구성 (2026-11-10, 사용자 결정): 깊이 카메라(RealSense D435i)를 쓸 수 없게 되어 USB 웹캠 2대만 쓴다. 위 = 웹캠 1대(작업 영역 + 키트 박스를 함께 봄, 높이 고정), 손목 = 웹캠 1대.
  - 이전 가정(위 = RealSense, 손목 = 웹캠, 전체·키트 = 웹캠)은 버림. 깊이로 얻던 것은 다음으로 바꾼다: 3D 위치 → 렌즈 왜곡 보정 + 평면 대응 변환, 색과 무관한 검출 → 한 색 검출(D06), 들어 올림 확인(높이) → 그리퍼 서보 값 + 원래 자리가 비었는지(S04).
  - 버린 대안: 빈 테이블 사진과 비교해 색과 무관하게 찾기. 그림자·조명 변화에 약하고, 실제 작업도 색을 지정하므로 이득이 적다.
  - 근거: 2026-11-10-discussion.md "카메라 구성 변경" 절.
- D06 블록 검출 = 한 가지 색(HSV) (2026-11-10, 사용자 동의): S02는 위치·각도 정확도만 재는 Step이라 눈에 잘 띄는 한 색을 쓴다. 블록끼리 붙어 있지 않다는 전제를 둔다(같은 색이 붙으면 나누기 어렵다).
- 위치 계산: 화면 좌표 → (렌즈 왜곡 보정) → 블록 윗면 높이 평면 기준 평면 대응 변환 → 테이블 좌표(mm) → 카메라-로봇 보정 → 로봇 좌표. 블록 윗면은 테이블보다 블록 한 변만큼 높아서 테이블 바닥 기준으로 계산하면 블록이 카메라 바로 아래에서 멀수록 바깥으로 밀려 보인다. 예: 카메라 높이 600mm, 블록 한 변 25mm, 바로 아래에서 200mm 떨어지면 약 8mm (계산값, 미측정). 그래서 기준 평면 높이(P12)를 블록 한 변으로 둔다.
- 접근 높이: 블록 위 30~50mm (사용자 확정 2026-11-10).
- 블록 각도: 위에서 본 블록 윤곽(최소 외접 사각형)을 테이블 평면 좌표로 옮겨 계산, 정육면체라 손목 회전 ±45° 안에서 정한다.
- LeRobot·카메라 라이브러리는 게이트웨이용 .venv와 분리된 별도 가상환경에 설치한다(LeRobot이 torch 등 큰 의존성을 고정하기 때문).
- D09 역할 분담 확정 (2026-11-11, 사용자 결정): CV+IK = 대상 선택·블록 위 접근·대략적인 손목 정렬 / ACT = 남은 오차 보정·내려가기·집기·바구니 투입·정상 HOME 복귀 / 별도 제어 로직 = 인계 여부·성공 확인·실패 감지와 검증된 복구 동작.
  - 바뀐 것: 2026-11-10 오후 "접근 오차가 10mm 안이면 집기는 계산, ACT는 홈부터 바구니까지"라는 분기를 버린다. 접근이 정확해져도 ACT의 시작점을 HOME으로 바꾸지 않는다.
  - 이유: 외부 분석(Astra_ULTRA)과 AI 검토 모두 이 구조를 적절하다고 봄. AI가 할 일을 접근 이후로 모으면 시작 상태가 좁아지고, 피지컬 AI 실습 방침(AI 최대 활용)과도 맞는다. 10mm는 접근 품질 참고 숫자일 뿐 ACT가 그 오차를 처리한다는 증거가 아니므로, S02는 "ACT에 넘길 수 있는 접근"으로 판정한다.
  - 대가: 잡았는지 확인하는 지점이 ACT 실행 도중으로 들어간다 → 감시 로직이 그리퍼 서보 위치·부하를 실시간으로 보고 중단해야 한다. ACT가 끝난 뒤 HOME 도착을 관절값으로 확인하고 계산 이동으로 정확히 맞춘다(위 카메라가 다음 블록을 보려면 팔이 비켜 있어야 함).
  - 시연 원칙: 실제 CV+IK 접근이 끝난 상태에서 시작하고, 접근 목표를 일부러 흔들어 보정 장면을 담는다.
  - 다시 판단할 조건: ACT 평가에서 처음 보는 위치 성공률이 낮고 원인이 바구니 투입·HOME 구간이면 그 구간을 계산 동작으로 되돌리는 것을 검토.
- D10 접근 오차 측정·보정 방법 (2026-11-11, AI 결정, 사용자 요청 "줄자 사용 최소화")
  - 측정: 손목 카메라 기준(블록이 두 부리 가운데 바로 아래일 때의 사진 위치·각도·크기)을 만들고, 이후 사진의 픽셀 차이를 mm·도·높이로 바꾼다. mm/픽셀은 팔을 ±10mm 움직여, 거리는 20mm 올려 블록 크기 변화로 잰다. 줄자 0회.
  - 보정 기록은 명령값 기준(명령한 위치 + 사진으로 잰 어긋남). 서보가 덜 가는 양까지 보정에 들어간다. 실행 단계 서보 보상을 나중에 넣으면 보정을 다시 모은다(두 번 보상 방지).
  - 버린 대안: 리더암 눈대중 정렬 기록(사람 오차·실제 관절값 기준이라 서보 덜 감이 남음), 줄자 실측(위에 떠 있는 그리퍼에서 재기 어려움), 실행 단계 서보 보상과 명령값 기준 보정 동시 적용(두 번 보상).
  - 한계: 손가락 길이 방향으로는 블록이 저절로 가운데에 오지 않아, 기준에 사람이 쥔 위치 오차(수 mm)가 들어간다 → 기준을 2회 만들어 비교.
- D11 ACT 인계 조건·시작 상태 확정 (2026-11-11, S02 결과로 정함, 사용자 요청 "넘어가는 조건 명시")
  - 시작 상태: 보정 없는 CV+IK 접근(`--corr none`, 수정한 손목 기준은 측정용). 벌린 두 부리 가운데를 블록 위 40mm(명령, 실제 약 33~35mm)로, 손목 회전을 블록 각도에 맞춤, 그리퍼 gripper_pregrasp(33.8).
  - 작업 영역: 로봇 좌표 x 95~ 145, y 100~ 220mm(받침대에서 약 133~ 263mm, 보정점 범위 안). 받침대 가까운 줄(x 95, y 100 부근)은 움직이는(검정) 손가락 쪽으로 7~10mm 치우침.

  - 이유: conda lerobot 환경에 이미 설치되어 있고, SO-101 설계 파일(URDF)을 그대로 쓸 수 있다. 해석식 직접 계산은 손목·그리퍼 끝 위치 차이까지 식으로 풀어야 해서 시간이 더 든다.
  - 방식: 손목 회전은 고정한 채 나머지 4개 관절로 "그리퍼 끝 위치 + 손가락 수직 아래"를 맞추고, 손목 회전은 블록 각도(90° 주기)로 따로 정한다. 모델에서 그리퍼 끝 점이 손목 회전축에서 조금 벗어나 있어(손목을 30° 돌리면 끝이 약 4mm 움직임, 계산) 두 과정을 손목 값이 멈출 때까지 반복한다.
  - 수직 자세가 관절 한계 때문에 안 되면 max_tilt_deg까지 기울어진 자세를 허용할 수 있다(기본은 허용 안 함).
  - 모델 계산 결과(2026-11-10, 시험): 수직으로 집을 수 있는 앞쪽 거리는 그리퍼 끝 높이 45mm에서 110~ 280mm, 65mm에서 135~ 260mm, 90mm 이상에서는 없음(손목 굽힘 한계 ±95°). 15°까지 기울기를 허용하면 65mm에서 130~ 325mm, 90mm에서 155~305mm. 실제 팔 범위는 S02-4에서 확인.
  - 버린 대안: LeRobot의 RobotKinematics.inverse_kinematics를 그대로 쓰기. 한 번 호출에 한 걸음만 계산하고 손목 회전이 아무 값이나 나와서, 감싸서 반복·검사하는 코드를 따로 만들었다.
- 화면 → 로봇 보정 방식 (현재 구현, 사용자 확인 전): 마커 대신 블록 9곳 + 리더암으로 짝을 모은다(2026-11-10 대화에서 AI 제안). 블록 윗면에서 짝을 지으므로 시차가 처음부터 없고, 화면 → 로봇 한 번으로 끝난다. 변환 코드(calib.py)는 어떤 방법으로 모은 짝이든 받는다.
- 현장 준비물: 블록, 자·줄자. 측정 목록은 project/measurements.json. 체커보드(렌즈 왜곡 보정)와 마커(키트 박스 표식)는 필요할 때만: 화면 가장자리 오차가 클 때, 키트 박스를 고정할 수 없을 때.

- 서보 정상 상태 오차(명령과 실제 관절각의 일정한 차이): 오늘 팔꿈치가 매번 약 2.4° 덜 갔다. 10분 실습: `arm.move_joints`로 같은 자세에 위·아래에서 각각 3번 들어가며 `arm.read()` 차이를 표로 비교.
- 측정 기준 자체의 검증(자기 채점 문제): 같은 기준으로 보정하고 평가하면 기준의 밀림은 드러나지 않는다. 10분 실습: straddle 사진 한 장에서 블록 25mm를 자로 양쪽 틈을 픽셀로 재 보기.
