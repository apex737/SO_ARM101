# 프로젝트

- 이름: KitBot — 주문에 맞춰 부품을 담는 작업 키트 구성 로봇 (SO-ARM101)
- 코드 위치: project/src/kitbot/ (게이트웨이 패키지), project/src/kitbot_exec/ (노트북 실행 코드: 검출·보정·기구학, 시험 project/src/tests_exec/), project/src/tests/ (시험), project/src/requirements*.txt (실행/개발/비전). 원 요구: project/src/pjt.md. 비전 예제: practice/00-CamExample/ (RGBD1/ RealSense·HSV 예제, RGBD2/ 엣지 검출. .venv에서 실행)
- 자주 쓰는 명령(가상환경·장치 확인·캘리브레이션·수집·학습): project/commands.md
- 현장 측정값 입력: project/measurements.json (사용자가 재서 채움 → AI가 계산값을 채우고 params.html로 옮김)
- 현재 작업: S05(ACT 학습: CV+IK 접근 이후 보정·집기·바구니·HOME). S02는 2026-11-11 통과, 인계 조건은 S02.md D11, 학습 유의사항은 project/Steps/S05.md. 다음 할 일: S05-1 시연 녹화 도구. 보류: AI 범위 2단계
- 환경·제약: 확인된 정보만 기록
  - 배치(사용자 결정 2026-11-09, 안 2): SO-ARM101 팔로워·카메라는 GPU PC에 USB 연결. GPU PC가 인식·정책 추론·서보 제어를 한 컴퓨터 안에서 수행한다. Pi는 게이트웨이(주문 API·대기열·DB·화면)로 GPU PC 실행 서버에 "red 하나 집어" 수준의 명령을 보내고 결과를 판정·기록한다.
  - Pi: Raspberry Pi 5 (사용자 답변). OS 미확인. Pi↔GPU PC: 이더넷·Wi-Fi 둘 다 가능.
  - GPU PC = 이 개발 노트북(사용자 확인): Windows 11, Python 3.11.9, RTX 4050 Laptop 6GB(실측), 개발용 가상환경 .venv/. 학습도 기본적으로 이 노트북에서 하고, 부족하다고 판단되면 클라우드를 나중에 검토.
  - 2026-11-10 작업 PC: Ubuntu 22.04, RTX 4050 Laptop 6GB(실측). 위 Windows 노트북과 같은 기기인지 미확인. 가상환경 2개: 게이트웨이·비전 예제용 .venv/(Python 3.11.18, requirements-dev + requirements-vision), 팔·학습용 conda 환경 lerobot(Python 3.12.16, LeRobot 0.6.0). 셸 PYTHONPATH에 ROS 2 Humble 경로가 있어 pytest는 `env -u PYTHONPATH`로 실행해야 함(실측).
  - 카메라(2026-11-10 변경, 사용자 결정): USB 웹캠 2대만 사용(Innomaker U20CAM 720P). 위 1대 = 블록 작업 영역(바구니는 화면에 없어도 됨), 손목 1대. 깊이 카메라(RealSense D435i)는 쓸 수 없음.
  - 팔: SO-ARM101 팔로워 + 리더암. 정책은 데이터 수집부터.
  - 작업대: 정육면체 블록, 한 번에 최대 8개(어려우면 조정 가능). 색 목록 미확인.
  - 집기 구조(2026-11-11 확정, S02.md D09): CV+IK로 블록 위 30~50mm 접근 + 손목 각도 맞춤(S02) → ACT가 남은 오차 보정·집기·바구니 투입·HOME 복귀(S05) → 별도 로직이 실패 감지·복구, HOME 도착 확인.
  - ACT 범위(2026-11-10 재검토로 변경, S02 결과 후 결정): 사용자 지적 "접근·회전을 계산으로 끝내면 집고 들어 올리기는 내려가기·닫기·올라가기뿐인데 ACT를 왜 쓰나". S02 접근 오차가 허용 범위 안이면 집기는 계산으로 하고 ACT는 홈부터 집어 바구니에 넣기까지 전체를 맡는 쪽(이전의 'AI 범위 2단계')을 검토, 계산 방식은 비교 기준·대비책·시연 자동 생성에 쓴다. 허용 범위 밖이면 ACT가 손목 카메라로 마지막 위치 보정 + 집기를 맡는다.
  - 놓기(2026-11-10 사용자 결정): 칸 구분 없이 바구니 안 아무 데나 놓는다. 바구니 가운데 위 자세 하나를 리더암으로 기록해 두고 그 자세에서 그리퍼를 연다. 바구니는 팔과 부딪히지 않게 조금 멀리 두고, BASKET 자세는 테두리보다 3~5cm 높게 비스듬히 기록해 떨어뜨린다(사용자 제안). 옮길 때는 어깨 회전을 마지막에 해서 테두리 위를 지나간다(pick.py).
  - 블록 작업 영역(2026-11-10 사용자): 위 카메라 화면 오른쪽에는 아무것도 들어오지 않으므로, 블록은 바구니 왼쪽 아래(화면 기준)에 둔다. 키트 표식·칸 좌표 계산·칸 확인은 하지 않는다. 바구니는 위 카메라에 보이지 않아도 된다.
  - 미확인: Pi OS, 블록 색 목록·크기, 웹캠 2대 동시 fps

## 우선순위·불변 조건·비목표
- 우선순위: 객체 인식 + 그리퍼 학습 전략(사용자: "결국 핵심") · 추론 속도 · 실패 인식과 재시도.
  - 신뢰성 기능(pjt.md 7번)은 6번까지 진행하며 필요할 때 옵션으로 붙인다. S01에서 이미 만든 부분은 유지한다.
  - 최종 구현 형태는 설계 토론으로 정해 간다(2026-11-09 시작).
  - 사용자 방침(2026-11-10): 피지컬 AI 실습이므로 AI를 최대한 활용하고 싶다. 고전 방법(계산·재생)은 문제를 쉽게 풀기 위한 절충안으로 본다.
- 불변 조건
  - 로봇은 한 번에 작업 하나만 수행한다.
  - DB가 주문·작업 상태의 원본이다. 재시작해도 접수한 주문을 잃지 않는다.
  - 물리 상태를 알 수 없으면(복구 실패·드라이버 무응답) 자동 진행을 멈추고 운영자 리셋을 기다린다.
  - 수행하지 않았거나 확인하지 않은 동작을 성공으로 기록하지 않는다.
- 비목표(현재): 다중 로봇, 인증·암호화(LAN 내부 가정), 클라우드 배포.
