# 요청받은 학습·실습

사용자가 실습·점검을 요청한 때만 읽는다. 사전 설문은 없다.

## 1. 시작
- 사용자가 지목한 실제 코드·결정·값부터 본다.
- 대상이 명확하면 바로 시작한다.
- 불명확할 때만 고를 대상 하나를 짧게 제안한다.

## 2. 설명
- 순서: 실제 예·숫자 → 표/그림 → 원리.
- 원인과 결과를 한 단계씩 연결한다.
- 흐름, 결정 근거, 변경 영향을 중심으로 필요한 부분만 설명한다.
- 불필요한 전문용어와 기초 반복을 피한다.
- 설명 요청에 시험을 억지로 붙이지 않는다.

## 3. 실습 만들기
- practice/NN-topic/에 문제·사용자 답·실행 방법·시험 입력을 둔다.
- 언어는 프로젝트 언어 또는 사용자가 원하는 것으로 한다.
- 별도 환경을 불필요하게 설치하지 않는다.
- 아래 5단계 중 필요한 단계만 골라 설계한다. 모든 단계를 의무로 하지 않는다.
- 직접 수행은 코딩 말고 설계·분석·진단일 수도 있다.

| 실습 설계 5단계 | 예: 링버퍼 가득 참 처리 | 기록할 이해 수준 |
|---|---|---|
| 따라가기 | 가득 찰 때 데이터 이동을 자기 말로 설명 | 설명 |
| 예측 후 실행 | 256바이트 버퍼에 300바이트가 오면 무엇이 남는지 예측하고 실행해 비교 | 설명 |
| 수정 | 처리 방식을 "새 값 버림"에서 "오래된 값 덮어쓰기"로 변경 | 수정 |
| 빈칸 | 가득 참 판정 조건 채우기 | 수정 |
| 직접 수행 | 빈 파일에서 넣기·꺼내기와 가득 참 처리를 작성해 시험 입력 통과 | 직접 수행 |

## 4. 도와주기
- 사용자의 빈칸과 답을 대신 채우지 않는다.
- 힌트는 요청할 때 한 단계씩 준다.
- 완성 답을 요청하면 제공한다. 단, AI가 제공한 부분은 이해 확인 증거로 쓰지 않는다.

## 5. 점검
- 미리 정한 기준과 실제 사용자 답·코드·시험 결과로 평가한다.
- 틀린 곳과 이유를 구체적으로 말한다. 원문은 보존한다.
- 장비·측정 문제나 타당한 가설 기각을 지식 오류로 처리하지 않는다.

## 6. 기록
- concepts.html의 해당 항목을 갱신한다.
  - level: 사용자가 실제로 해낸 가장 높은 수준(설명 / 수정 / 직접 수행).
  - evidence: 문항·과제, 기준, 사용자 원문 또는 원문 경로, 결과, 힌트 사용, 확인 조건.
- 대체된 이전 평가는 git에 남는다.
- 설명만 들었으면 미확인이다.
- 사용자가 실제로 수행했을 때만 확인됨으로 바꾼다.

## 7. 확장과 재확인
- 관련 기능을 엮어 설명하거나 다른 조건에서 수행하는 과제는 학습 목표에 필요할 때만 쓴다.
- 다른 날 재확인은 사용자가 요청할 때 한다.
- 자동 복습이나 자동 다음 시험은 없다.

## 8. 구현으로 돌아가기
- 구현 요청이 오면 즉시 진행한다. 실습 미완료는 구현을 막지 않는다.
- 학습용 수정은 원칙적으로 practice/에서 한다.
- 제품 코드 반영은 구현 요청의 범위에 맞춘다.
